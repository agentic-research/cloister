## Master problem statement (all specialists read)

The just-shipped DO saga moves `cloister/credential-isolation/v1` from
draft to production-ready. The load-bearing change shape:

**Before (D-prefix):**
- `CredentialStore` interface had a single method: `resolve(peerFp, service) → CredentialLookup | null`
- Production composition wired `InMemoryCredentialStore` (a Map) at the route level
- Plaintext credential bytes lived in the route handler's memory after resolve

**After (D-suffix, shipped today):**
- `CredentialStore` interface gains optional `forward(peerFp, service, callerSub, request) → Response`
- `VaultDoCredentialStore` implements `forward` by delegating to `env.VAULT_STORE.idFromName(bundleIdName).proxyRequest(...)` — plaintext stays inside the DO trust boundary (ADR-0013)
- `VaultProxyRoute` constructor accepts deps; at request time `selectCredentialStore(env)` picks via three-branch priority:
  1. Explicit `deps.credentials` override → use verbatim
  2. `env.VAULT_STORE` present → lazily construct + memoize `VaultDoCredentialStore({env, bundleIdName: "router"})`
  3. Otherwise → `InMemoryCredentialStore` fallback (dev)
- Route handler branches on `credentialStore.forward` — when defined, delegate the full Request; otherwise resolve+inject as before
- Per-bundle isolation seam is the `bundleIdName: string` constructor parameter (default `"router"` until notme-as-bundle wires `"notme"` per ADR-0021)

### What "load-bearing" means here

The five claims this code now defends (see `README.md§"Load-bearing claims"`):

1. **Plaintext credentials never cross the response boundary** — caller observes request/response/error/log/metric, MUST NOT reconstruct credential value
2. **Identity-scoped access** — `allowedSubs` glob enforced before injection
3. **Audit by receipt** — every proxy call commits to `peer_receipts` row; receipt MUST NOT carry credential value
4. **§9.4.b constant-time 404** — peer-existence + credential-existence non-distinguishable from the wire (status code + body bytes collapse)
5. **Per-bundle isolation via `idFromName`** — bundle A's `bundleIdName: "X"` cannot reach bundle B's `bundleIdName: "Y"` storage (ADR-0021)

Findings that break any of these are P1. Findings that erode them under specific edge cases are P2. Findings that are theoretical-but-not-exploitable are P3.

### F1 — manifest `defaultAllowedSubs` gate is silently bypassed on the forward path (P2, high confidence)

**Evidence:**
- `src/routes/vault-proxy-route.ts:176-183` — when `credentialStore.forward` is defined and `serviceConfig !== null`, the route hands the request straight to the store with no `checkAccess(serviceConfig.defaultAllowedSubs, peerFp)` call.
- Contrast with the resolve+inject branch: `src/routes/vault-proxy.ts:139-141` runs `if (!checkAccess(req.serviceConfig.defaultAllowedSubs, req.verifiedLease.peerFp)) return rejection(403);`.
- Inside vault DO (`src/vault-store.ts:487`) the access gate is `checkAccess(allowedSubs_FROM_ROW, callerSub)` against the per-row `allowed_subs_json` value, NOT the manifest's `defaultAllowedSubs`.

**Exploit shape:** Operator declares `defaultAllowedSubs: ["skill/openai/*"]` on a service in the manifest believing this is "the" access list. Some prior call (or an out-of-band put) stored the credential with row-level `allowedSubs: ["*"]` or with a peerFp the manifest no longer trusts. On the forward path the manifest gate is dead code; the row-level glob wins. Two ACLs exist, only one is enforced per path, and which one fires depends on whether `credentialStore.forward` is truthy — i.e. on a composition-root decision invisible at manifest review.

A more concrete attack chain: compromised admin tooling that can call `putCredential` (out-of-band, not through the proxy) writes a permissive `allowedSubs: ["*"]` row. Reviewers later harden the manifest with a tight `defaultAllowedSubs`, see green tests on the resolve path (in-memory store, used in unit tests), and ship. Production hits the forward path; manifest tightening is silently dropped.

**Suggested defense:** On the forward branch, run `checkAccess(serviceConfig.defaultAllowedSubs, verifiedLease.peerFp)` BEFORE `store.forward(...)` and collapse rejection to the same `CONSTANT_TIME_ERROR_BODY` 404 the route already emits. Layered enforcement: manifest gate at the route AND row gate inside the DO. Alternatively, spec the divergence as intentional (manifest's `defaultAllowedSubs` is only a fallback for putCredential, not a request-time gate) and document it in `cloister-spec/credential-isolation/v1/README.md` — but right now the docstring at `vault-proxy-route.ts:165` ("preserves the §9.4.b oracle closure") implies the gates are layered and they aren't.

### F2 — falsy-`forward` composition footgun silently downgrades a vault-DO store to plaintext-in-route (P2, medium confidence)

**Evidence:**
- `src/routes/vault-proxy-credential-store.ts:72-77` — `forward?` is OPTIONAL on the interface.
- `src/routes/vault-proxy-route.ts:176` — the selector is a truthy check: `if (credentialStore.forward && ...)`.
- Any `CredentialStore` impl with `forward: undefined`, `forward: null`, or a deletion-by-reflect shim collapses to the resolve+inject branch (lines 185-201), which expects to handle plaintext credential bytes locally.
- A partial mock, a JSON-deserialized store, or a class that gates `forward` behind a feature-flag that disables it (and sets the field to undefined rather than leaving the slot unimplemented) all hit this.

**Exploit shape:** A future bundle (notme-as-bundle, ADR-0021) ships a `NotmeVaultStore extends VaultDoCredentialStore` that conditionally exposes `forward` only when some env-flag is set. If the flag is unset, the route falls through to `resolve()` — which the future impl might implement (because the interface allows it) — and the credential bytes flow through the route's memory, breaching ADR-0013. The fail-open direction (forward absent → plaintext path) is the wrong default for a slice-grant invariant.

**Suggested defense:** Two non-mutually-exclusive options. (a) Make `forward` REQUIRED on `CredentialStore` and ship a stub on `InMemoryCredentialStore` that throws `"in-memory store does not support forward"` — the composition root must explicitly opt INTO the resolve path by picking the in-memory class, not by omitting a method. (b) Add a constructor-time invariant on `VaultProxyRoute`: if any dep store has `forward === undefined`, brand the route as `mode: "dev-resolve-injection"` and require an explicit `allowResolveMode: true` flag in `VaultProxyRouteDeps`. Today the route silently downgrades; the fail direction should make the operator opt in.

### F3 — selectCredentialStore memoizes env reference; stale-env race is theoretically reachable across binding rebinds (P3, low confidence)

**Evidence:**
- `src/routes/vault-proxy-route.ts:127-129` — `this.vaultDoStore ??= new VaultDoCredentialStore({ env, bundleIdName: "router" });` captures `env` (param) into the store's `this.env` (`src/routes/vault-do-credential-store.ts:62`).
- Once memoized, `vaultDoStore` is never invalidated. All subsequent forward calls go through `this.env.VAULT_STORE.idFromName(...)` using the FIRST env reference observed.
- The route ALSO chooses between the memoized vaultDoStore and the in-memory fallback per-request based on the CURRENT `env.VAULT_STORE` (line 127). So request N can fall through to the in-memory path while a previously-constructed vaultDoStore still holds a stale env.

**Exploit shape:** Workerd doesn't normally rotate env bindings mid-isolate-lifetime, so this is mostly theoretical. The two paths I can see:
1. **Test harness** that swaps env between describe blocks while reusing a single `VaultProxyRoute` instance: the second-test env's VAULT_STORE rebind is ignored, all forward calls route to test-1's namespace. Real risk for shared route fixtures.
2. **Future hot-reload** (if ADR-0023's `CLOISTER_DO_PATH` workflow ever supports binding swap without a worker restart): credential traffic flows to the OLD namespace silently, breaking the manifest contract operators just rolled out.

**Suggested defense:** Either (a) reconstruct the store when env identity changes — `if (this.vaultDoStore?.env !== env)` invalidate-and-rebuild; or (b) make the memoization explicit per-env via `WeakMap<Env, VaultDoCredentialStore>`. The current `??=` pattern fails the "binding-rebind safety" property silently and there's no test that locks it down. Lower-effort: drop the memoization entirely — the construction is a single `new` with no I/O, and the per-call overhead is trivial vs. correctness clarity.

### F4 — `bundleIdName: "router"` is hardcoded in the route, defeating ADR-0021's per-bundle isolation seam until rewired (P2, high confidence)

**Evidence:**
- `src/routes/vault-proxy-route.ts:128` — `new VaultDoCredentialStore({ env, bundleIdName: "router" })` is a string literal.
- `src/manifest/runtime.ts:187-189` — manifest-instantiated `VaultProxyRoute` passes only `{ services: ... }`, no `bundleIdName`, no `deps.credentials`. The route auto-selects with `"router"`.
- `src/vault-store.ts` file header (lines 50-83) declares the cross-bundle isolation contract as "binding layer = which DO instance" with `idFromName(<bundleIdName>)` as the seam.
- Today the only manifest-instantiated path is cloister-router so `"router"` is correct. But the moment a second bundle ships via the same manifest runtime — or someone copies this code path — every route resolves to the SAME `idFromName("router")` DO instance, collapsing the binding-layer isolation onto only the SQL-row-layer defense-in-depth (subject_fp PK).

**Exploit shape:** Future bundle (notme-as-bundle, or any second `vaultProxy` route declared in manifest) inherits `"router"` via the auto-select. Two bundles now share a DO instance. SQL-PK isolation still holds for read/write of `(subject_fp, service)` rows, but: (a) `proxyRequest` no longer benefits from binding-layer separation; (b) any future schema change in vault DO that drops the composite PK reverts to a flat namespace for all bundles at once; (c) DO-wide rate-limit (`MAX_INFLIGHT` per `#checkInflight`) is shared across bundles, enabling cross-bundle DoS.

**Suggested defense:** `bundleIdName` MUST come from the manifest/composition root, not be a literal. Options:
1. Lift to manifest: add `bundleIdName: string` to the `vaultProxyRoute` schema, plumb through `instantiate()` in `runtime.ts:187`, default-but-warn on unset.
2. Lift to env: read from `env.CLOISTER_BUNDLE_NAME` (or similar), surface a missing-binding error at `selectCredentialStore` time.
3. Lift to constructor: add `bundleIdName?: string` to `VaultProxyRouteDeps`, require manifest builder to provide it.

In all three, a lint rule should fail the build if two `vaultProxy` route declarations resolve to the same `bundleIdName`. The current code structure makes "wire a second bundle" a single-line copy that silently collapses isolation.

### F5 — error-responses.md spec REQUIRES `Cache-Control: no-store` on all error paths; no implementation emits it (P2, high confidence)

**Evidence:**
- Spec at `cloister-spec/credential-isolation/v1/wire/error-responses.md:124-128`: "All error responses MUST set: `Content-Type: application/json`, `Cache-Control: no-store`".
- `src/routes/vault-proxy-route.ts:151-153,167-169` — both route-level error responses set ONLY `content-type`.
- `src/routes/vault-do-credential-store.ts:96-100` — `jsonResponse(503|502)` sets ONLY `content-type`.
- `src/routes/vault-proxy.ts:448-453` (`rejection`) — sets ONLY `content-type`.
- `src/vault-store.ts:404-414, 419-430` — 429 paths set `retry-after` but no `cache-control`.
- Inside vault DO, the 404 response (`vault-store.ts:476-481, 491-495`) uses `Response.json(...)` which does NOT add `Cache-Control`.

**Exploit shape:** An intermediary cache (CF edge cache, corporate proxy, browser cache, even `service-worker` Cache API in a hosting frontend) may cache the 404/403/401 collapse responses keyed on URL+method. Two different peers hitting the same `/vault/proxy/<service>/<path>` get the cached response. While the body is byte-equal across "access denied" outcomes (preserving the §9.4.b collapse intentionally), caching means: (a) operator rotates a credential, allowedSubs changes; the OLD 404 keeps serving from cache until TTL expires — peer falsely believes no credential exists; (b) cached error responses become a probing-friendly side channel (an intermediary that DOES distinguish "cached vs uncached" via timing leaks the enumeration bit that the body collapse was meant to close).

This is also a cross-reference candidate to enumeration-oracle-hunter — see Cross-references below.

**Suggested defense:** Lift error-response construction into a single helper `errorResponse(status, body)` that always sets `Cache-Control: no-store` AND `Content-Type: application/json`. Call it from all five sites listed above. Add a spec-conformance test: assert every error path emits the required headers. This is a one-line per-call-site fix plus one test; the spec is already explicit.

### F6 — `VaultDoCredentialStore.forward`'s 502 catch audited; no bypass found (P3, informational)

**Evidence:**
- `src/routes/vault-do-credential-store.ts:86-92`:
  ```ts
  try {
    const stub = ns.get(ns.idFromName(this.bundleIdName)) as DurableObjectStub & VaultProxyRpc;
    return await stub.proxyRequest(peerFp, service, callerSub, request);
  } catch {
    return jsonResponse(502, { error: "upstream_unavailable" });
  }
  ```
- The bare `catch` catches everything including non-Error throws (DOMException, primitive throws, Symbol throws). Synchronous throws inside the try (`ns.idFromName`, `ns.get`, calling an undefined `stub.proxyRequest`) are all caught.

**Audit verdict:** No bypass found. Listed for completeness — the catch construction is correct but wide enough that the safety property relies on JS catch semantics. Synthesis lead should weight as "audit OK."

### F7 — `forward` path passes `peerFp` as BOTH `subjectFp` AND `callerSub`; conflation prevents the "admin puts cred, peer consumes" pattern from working at the proxy (P3, medium confidence)

**Evidence:**
- `src/routes/vault-proxy-route.ts:177-182` — `credentialStore.forward(verifiedLease.peerFp, service, verifiedLease.peerFp, request)`.
- `src/vault-store.ts:155-180` (`VaultStoreRpc` interface) — distinguishes `subjectFp` (the credential row owner) from `callerSub` (the entity asking to use it). `#proxyRequestInner` (lines 447-505): `WHERE subject_fp = ? AND service = ?`, then `checkAccess(allowedSubs, callerSub)`.
- By passing peerFp for both, the v1 design collapses to "each peer can only access credentials they themselves stored AND that they themselves are in the allowedSubs of." `allowedSubs` becomes vestigial — `subject_fp = peerFp` already requires the caller IS the owner.

**Why this is a finding (not just a design observation):**
The spec's multi-tenant model implies that an operator/admin can put a credential under SUBJECT_FP = service-owner, and grant ACCESS to multiple peer fingerprints via allowedSubs. The forward path's hardcoded `peerFp/peerFp` collapse makes this impossible from the proxy endpoint — even if an admin out-of-band puts `(adminFp, service, allowedSubs=[peerA])`, peerA hitting the proxy asks for `(peerA, service)` which doesn't exist → 404. Operator footgun: tries to set up "admin puts cred, peers consume," can't make it work, and the constant-shape 404 prevents debugging.

**Suggested defense:** Decide the model in spec. If self-only, document `allowedSubs` is redundant and call sites should set `allowedSubs: [peerFp]` (long-term drop the column). If admin/delegated, the route needs a `subjectFp` derivation distinct from `peerFp` — probably via the manifest's service config declaring the owning subject.

### F8 — `parseVaultProxyPath` accepts arbitrary `service` strings; no shape validation (P3, low confidence)

**Evidence:**
- `src/routes/vault-proxy.ts:462-480`: `service = tail.slice(0, firstSlash)` (or `tail`). Only rejects empty.
- `service` flows into `serviceConfig = this.services(service)` (route line 160) and into `stub.proxyRequest(_, service, _, _)` (vault-do-credential-store.ts line 88).
- Service names like `..`, `%2F`, or `service%00poisoned` are accepted. The lookup will return null for an undeclared name → 404 (no direct privilege escalation).

**Exploit shape:** No direct exploit. Future-fragility: the service name is request-controlled and feeds vault DO SQL (safe — parametrized) and Shape-V body (safe — JSON.stringify escapes). Any future code that adds the service name to a path join, log line, or metric label without sanitizing inherits unvalidated input.

**Suggested defense:** Validate `service` at `parseVaultProxyPath` against a strict regex (e.g. `/^[a-z][a-z0-9_-]{0,63}$/`) and return `null` for non-matching. Confidence low — purely hardening, no current exploit.

> **Scope reminder:** New lazy + memoized `VaultDoCredentialStore`

### Resolved-at-audit (clarifying observations, not findings)

**RA-1: Lazy-construction race is not exploitable.** `selectCredentialStore`
(`src/routes/vault-proxy-route.ts:128`) uses `this.vaultDoStore ??= new
VaultDoCredentialStore({env, bundleIdName: "router"})`. Workerd / V8
runs JS as a single thread; `??=` is a synchronous expression that
runs atomically between any two await suspension points. The
`VaultDoCredentialStore` constructor (`vault-do-credential-store.ts:61-64`)
does NO IO and NO await — it just assigns two fields. Two concurrent
first-callers may both reach `selectCredentialStore`, but they cannot
both evaluate `??=` interleaved. Even in the absolute-worst-case
where some future refactor accidentally inserts an await before the
assignment, the only consequence would be allocating one extra closure
+ assigning the slot twice — both instances would still point at the
same `env.VAULT_STORE.idFromName("router")` DO. Not a DoS surface.

**RA-2: Memoization is per-isolate, not per-request.** `instantiate(manifest)`
is called ONCE at module top-level in `src/index.ts:26`. There is
exactly one `VaultProxyRoute` instance per Worker isolate lifetime,
so `this.vaultDoStore` survives across all requests served by that
isolate. The memoization is real and meaningful. Cold-start cost is
one allocation per isolate cold-start, not per request.

### F1 — 502 fallback path is unbudgeted, unlogged, and unaccounted [P2]

**Evidence:**
- `src/routes/vault-do-credential-store.ts:86-91`:
  ```ts
  try {
    const stub = ns.get(ns.idFromName(this.bundleIdName)) as DurableObjectStub & VaultProxyRpc;
    return await stub.proxyRequest(peerFp, service, callerSub, request);
  } catch {
    return jsonResponse(502, { error: "upstream_unavailable" });
  }
  ```
- The `catch {}` is bare — no variable bound, no logging, no metric
  emission, no per-caller counter increment.
- The route layer does NOT inspect the response (`vault-proxy-route.ts:177-183`
  returns `credentialStore.forward(...)` verbatim) so the 502 is
  invisible to the outer composition.
- No rate budget is decremented on the 502 path. The vault DO's
  `#consumeBudget` was never reached because the RPC threw before
  any DO-side code ran (or threw mid-way — same blind path).

**Exploit shape (attacker-cost asymmetry):**
An attacker who can force `stub.proxyRequest` to throw — DO eviction
storm, transient binding misconfiguration, intentional malformed-`Request`
serialization across the RPC boundary if such exists, deliberate
network blip targeted at the colo — gets:
- Cost to attacker: 1 HTTPS POST per probe (the cheapest possible
  HTTP request: empty body, lease header).
- Cost to defender: 1 lease verification (wasm32 cert chain verify +
  Ed25519 sig verify + TrustStore RPC for nonce dedup + epoch +
  validity-window check — see `src/routes/lease-middleware.ts`) +
  1 DO stub allocation + 1 RPC attempt + 1 RPC throw + 1 JSON
  encode for the 502 body. The lease verification alone is the
  most expensive thing per request in the entire route — and it
  runs BEFORE the catch is reachable.
- Amplification: **1 RPC : 1 wasm cert verify + 1 Ed25519 verify +
  1 TrustStore RPC + 1 DO allocate + 1 RPC throw + 1 JSON encode**.
  Roughly 1:6 with the cert-verify being the dominant cost.
- Per-caller accounting: ZERO. An attacker holding a single valid
  lease can mount this attack indefinitely against the gateway
  CPU budget; the F1 token-bucket inside vault DO never fires
  because the catch is on the cloister-router side of the RPC.

**Blast radius:** Cross-isolate. Workerd's single-threaded handler
will be CPU-bound on cert verification, starving co-resident routes
served by the same isolate (every other `EdgeRoute` in the manifest
running through `instantiate()`'s output). The 502 path is the
ONLY path in the entire vault-proxy surface that doesn't decrement
any budget, anywhere.

**Suggested defense:**
1. The route layer (NOT `VaultDoCredentialStore.forward`, which is too
   deep) should maintain a per-peer "recent 5xx from forward" counter
   with exponential decay. Three 502s in a sliding window → quarantine
   the peer for 30s with a 503 fast-reject (no cert verify on the
   reject path).
2. The catch in `forward` should bind the error and emit a structured
   `vault.forward_throw` log line for observability-auditor's silence-is-evidence
   pass — otherwise the 502 is alert-deaf.
3. The 502 response should include `Retry-After: 30` (or similar) so
   well-behaved clients back off; per `wire/error-responses.md` §125-135
   the wire spec MANDATES `Cache-Control: no-store` and SHOULD set
   `X-Content-Type-Options: nosniff` — `jsonResponse` at line 95-100
   sets NEITHER, in violation of the wire spec.

**Confidence:** High (code-cited; spec-cited; cost model is concrete).

### F2 — Cross-bundle inflight cap is shared, not per-peer [P2]

**Evidence:**
- `src/vault-store.ts:190`: `private inflight = 0;` — a single
  scalar per-DO-instance.
- `src/vault-store.ts:314-326`: `#checkInflight()` checks
  `this.inflight >= RATE_LIMITS.MAX_INFLIGHT` (16, per `vault/src/rate-bucket.ts:22`).
- `vault-do-credential-store.ts:25-26` + `vault-proxy-route.ts:128`:
  the singleton bundle name `"router"` means EVERY caller through the
  cloister-router shares ONE `idFromName("router")` DO. Until per-bundle
  notme lands (the ADR-0021 work flagged in the file header), all
  identity-isolated peers contend for the same 16-slot bucket.

**Exploit shape (attacker-cost asymmetry):**
- Attacker peer A holds a valid lease + a credential row with their
  own `allowedSubs`. They `POST /vault/proxy/<their-svc>/<deep-upstream-path>`
  where the upstream URL is chosen to be a slow / unreachable endpoint
  (e.g., a domain they control that holds the TCP connection open for
  60 seconds before responding).
- Each in-flight `proxyRequest` increments `inflight++` (line 433) and
  holds the slot until the upstream returns (line 504-505: `await fetch(proxyReq)`).
- 16 concurrent attacker requests saturate the bucket. The 17th request
  — from ANY peer, attacker or not — gets a 429 with `retry-after: 1`
  (line 411).
- Cost to attacker: 16 long-poll HTTP connections + 16 valid leases.
- Cost to victim peer B: every `proxyRequest` 429s for the duration
  of attacker's slow-upstream hold.
- Amplification: 1 attacker slot : 1 victim slot (1:1), but the
  victim's "denied" outcome propagates to N concurrent victim peers.
  So 16 attacker slots : ALL victim peers (1:N).

**Blast radius:** All co-tenants of the `router` bundle. Until ADR-0021
notme-as-bundle lands (per file header comment at `vault-do-credential-store.ts:25-26`),
this is every peer the gateway serves.

**Suggested defense:**
- Sharded inflight bucket: keep `inflight` per `subjectFp` (a `Map<string, number>`),
  with per-peer cap of `MAX_INFLIGHT / expected-concurrent-peers` (say 4)
  and a global cap of `MAX_INFLIGHT` (16). This bounds the noisy-neighbor
  effect.
- Per-upstream-host timeout (the `await fetch(proxyReq)` at line 504
  is unbounded — workerd's default request limit is 30s but a single
  peer holding 16 slots for 30s each is 480 slot-seconds of denial).
  AbortController with a 5-second wall on the upstream fetch.

**Confidence:** High (the scalar `inflight` field is verbatim
shared; per-peer keying is absent).

### F3 — 429 from vault DO carries hardcoded `retry-after: 1` for inflight overflow [P3]

**Evidence:**
- `src/vault-store.ts:411`: `"retry-after": "1"` is a string literal
  for the inflight-overflow 429 path.
- This contradicts `wire/error-responses.md:74`: "Conformant
  implementations MUST set `Retry-After` to a sensible value (not 0,
  not negative). The default emitter uses the token-bucket's computed
  `retryAfterSec`."
- For the SUSTAINED 429 path (line 427: `String(budget.retryAfterSec)`)
  this is correct. For the BURST 429 path (line 411) it's a hardcoded
  1.

**Exploit shape:** Marginal. An attacker discovers that the inflight
overflow `retry-after: 1` is suspiciously fast vs. the sustained
overflow's variable retry-after — and uses the difference as an
oracle to determine which 429 they hit (sustained vs burst). This
leaks at most the F1 internal counter state.

**Amplification:** 1 RPC : 1 oracle bit. Compose-attack: see Cross-references.

**Suggested defense:** Compute a real retry-after for the burst gate
based on `inflight - MAX_INFLIGHT` and a target slot-release rate;
or set it to a constant ≥ the sustained-retry minimum to make the
two paths indistinguishable on the wire.

**Confidence:** Medium (the leak is real; whether it composes into a
useful oracle attack depends on what an adversary correlates with).

### F4 — Wire-spec headers absent on `VaultDoCredentialStore` 502 + 503 paths [P2]

**Evidence:**
- `src/routes/vault-do-credential-store.ts:95-100` (`jsonResponse`):
  ```ts
  return new Response(JSON.stringify(body), {
    status,
    headers: { "content-type": "application/json" },
  });
  ```
  No `Cache-Control: no-store`. No `X-Content-Type-Options: nosniff`.
- `wire/error-responses.md:124-138`: "All error responses MUST set
  `Content-Type: application/json` [and] `Cache-Control: no-store`
  (prevents intermediaries from caching oracle-shaped responses).
  Implementations SHOULD set `X-Content-Type-Options: nosniff`."
- Applies to BOTH the 502 (`upstream_unavailable`) AND the 503
  (`vault_unavailable`) paths — neither one sets the required
  no-store header.

**Exploit shape:** An attacker behind a caching intermediary (CDN,

be cached, then replay it for victims who would otherwise have

`Cache-Control: no-store` violates the §9.4.b oracle-closure spirit

substrate.

**Amplification:** Indirect — depends on intermediary cache behavior.
Self-limiting in pure cloister deployments but a footgun.

**Suggested defense:** `jsonResponse` should always emit:
- `Cache-Control: no-store`
- `X-Content-Type-Options: nosniff`
Trivial fix; spec-pinned requirement.

**Confidence:** High (spec is explicit; code is missing the headers).

### F5 — Lease verification is the most expensive thing per request and runs unconditionally before the inflight gate [P2]

**Evidence:**
- `src/routes/vault-proxy-route.ts:149`: `await this.leaseVerifier(request, env, parsed)`
  runs FIRST in `handle()`.
- `defaultLeaseVerifier` at line 210-230 calls `verifyAndUpsertLease`
  which (per the file header in `lease-middleware.ts` mirrored at
  `CLAUDE.md`): does cert-chain verify (wasm32) + Ed25519 sig verify
  + TrustStore RPC + epoch + validity-window + nonce dedup. Per
  request. Per peer. No fast-path cache.
- ONLY AFTER lease verification passes does the route reach
  `selectCredentialStore` → `forward` → vault DO's `#checkInflight`.
- An attacker holding ANY valid lease can probe-spam the route. Each
  probe costs the attacker 1 HTTP POST; costs the defender 1 full
  cert chain verify + 1 Ed25519 verify + 1 TrustStore RPC roundtrip.
- The TrustStore RPC roundtrip itself (per CLAUDE.md `peer_lease_counters`
  table) is a write to a singleton DO — see also: TrustStore is the
  cluster-wide singleton per ADR-0012. So every vault-proxy probe
  amplifies into one TrustStore-DO write. Attacker can drive
  TrustStore saturation through vault-proxy probes.

**Exploit shape (attacker-cost asymmetry):**
- Attacker: 1 valid lease (one-time mint cost from notme) + N HTTP POSTs.
- Defender per POST: cert verify + sig verify + TrustStore RPC write
  (cross-DO IO + SQL exec) + service-config lookup + (if cred exists)
  vault DO call.
- Amplification: 1 RPC : ~5 expensive operations + 1 cross-DO write.
- If attacker spams to undeclared services, the route 404s at
  `vault-proxy-route.ts:166-170` AFTER cert verify but BEFORE the
  service check fires. So even probing for non-existent services
  costs the defender the full lease verify.

**Blast radius:** TrustStore singleton DO (cluster-wide). Saturating
TrustStore means lease verification slows everywhere — including
all OTHER routes that use lease verification (McpEdgeRoute,
disclosure endpoint). This is a cross-route blast radius via the
shared TrustStore.

**Suggested defense:**
- Per-peer "successful lease verification" cache with short TTL
  (5-15 seconds). After the first verify, subsequent requests
  from the same peer with the same lease header bytes can fast-path
  to the cached result. Cache invalidated by epoch advance or
  TrustStore signal.
- Per-peer denial counter at the route layer: after N rejected
  attempts in window W, fast-reject without running lease verify
  (constant-time 401 from a cheap counter check).
- TrustStore needs its own per-caller rate limit (a `#checkInflight`-
  equivalent for the TrustStore nonce-dedup write path) — out of
  scope for this cycle but file as follow-up.

**Confidence:** High (lease-middleware cost shape is documented;
no fast-path cache exists in the route).

### F6 — `bundleIdName: "router"` is a global string constant; all in-cluster traffic shares one DO [P2]

**Evidence:**
- `src/routes/vault-proxy-route.ts:128`: `new VaultDoCredentialStore({ env, bundleIdName: "router" })` —
  the literal string `"router"` is hardcoded.
- `src/routes/vault-do-credential-store.ts:25-26` comment:
  "Today the only caller is cloister-router (`bundleIdName: "router"`);
  notme-as-bundle (cloister-db99cd) will pass `"notme"` when that lands."
- `vault-store.ts:14-15`: vault is "SINGLETON per cluster, reached via
  `env.VAULT_STORE.idFromName(\"cluster\")`. Same convention as TrustStore."
- BUT `vault-proxy-route.ts:128` uses `"router"`, not `"cluster"`. So
  the vault DO instance reached by this route is `idFromName("router")` —
  a DIFFERENT DO instance than the canonical singleton `idFromName("cluster")`.

**Implication for DoS:**
- All requests serviced by `VaultProxyRoute` hit the same `router`
  DO. The F2 finding (shared inflight cap) compounds: there is no
  per-peer sharding AND no per-bundle sharding (because there's only
  one bundle today, by name). 16 inflight slots gate the entire
  vault-proxy surface for the entire cluster.
- The mismatch with `vault-store.ts`'s documented `"cluster"` singleton
  naming convention is itself a finding — it means the `router`
  vault DO is a SEPARATE DO instance from any other code reaching
  via the documented convention. Either the doc is stale or this
  route is wired to the wrong DO instance.

**Exploit shape:** Composes with F2. Single shared inflight bucket
across all peers. See F2 for the slow-upstream attack.

**Suggested defense:**
- Either: align the name with the documented convention (`"cluster"`)
  AND ensure all callers reach the same DO instance.
- Or: explicitly document that `router` is intentional and the
  `cluster` naming convention is for non-vault-proxy paths.
- The ADR-0021 per-bundle work mitigates this when it lands, but
  until then the route should AT LEAST shard by `verifiedLease.peerFp`
  hashed into a small bucket count (say 4-16 DO instances) so a
  single peer cannot fill the entire shared inflight pool.

**Confidence:** High for the hardcoded-name observation; Medium for
the DoS implication (per-bundle sharding is on the roadmap but
hasn't shipped, leaving the gap open today).

### F7 — Per-route allocation cost under burst: rate_buckets table grows unbounded [P3]

**Evidence:**
- `src/vault-store.ts:261-264` comment: "Open: the rate_buckets table
  grows with unique subject_fps. Pre-1.0 this is bounded by notme's
  cert-mint rate (itself rate-limited). Filed as future cleanup:
  LRU eviction or TTL sweep, mirror the seen_nonces retention sweep
  playbook."
- `#consumeBudget` (line 285-290) UPSERTs into `rate_buckets` on
  EVERY call, accept or reject — so even a 429'd subject_fp gets
  a row written.
- New attack vector enabled by the D-track: the route now forwards
  every credential-store call to vault DO's `proxyRequest`, which
  calls `#consumeBudget` on the `subjectFp` (the peer's lease cert
  fp). If an attacker can mint many distinct cert fingerprints (via
  notme cert-mint amplification, or compromised in-cluster bundle
  with mint capability), each one writes a new row to `rate_buckets`.

**Exploit shape:**
- Attacker mints N distinct cert fingerprints (or replays leases
  with N distinct `peerFp` values — subject to notme rate limits).
- Each one makes 1 vault-proxy call → 1 row in `rate_buckets`.
- Rows are NEVER evicted (per the open-todo comment above).
- The SQL file grows; PRAGMA table_info + future schema migrations
  slow down; cold-start SQL provisioning slows.
- Cost to attacker: 1 cert mint + 1 HTTP POST per row.
- Cost to defender: 1 SQL INSERT + 1 row of permanent state per
  attacker-controlled fingerprint.
- Amplification: 1:1 today; compounds over time (SQL file size
  growth is monotonic).

**Suggested defense:** Mirror the seen_nonces sweep playbook
referenced in the comment — TTL-based eviction (e.g., drop rows
where `last_refill_ms < now - 7*86400*1000`). Run as alarm in the
DO. The TODO is already filed; this finding upgrades urgency
because the new D-track adds a hot path that feeds this table.

**Confidence:** Medium (the leak is real and acknowledged; whether
N-distinct-peer-fps is achievable depends on notme's mint rate
limits, which are out of scope).

### O1 — Selection-side oracle: store class observable from wire body **[P1]**

**Evidence.** `src/routes/vault-proxy-route.ts:125-132` (`selectCredentialStore`)
picks `InMemoryCredentialStore` (no `forward`) vs `VaultDoCredentialStore`
(has `forward`). The route branches at `:176`:

```ts
if (credentialStore.forward && parsed !== null && serviceConfig !== null) {
  return credentialStore.forward(verifiedLease.peerFp, service, verifiedLease.peerFp, request);
}
// else: legacy resolve+inject → vaultProxyHandler(...)
```

The two paths emit **byte-distinguishable** errors for the same input
(authenticated peer, no credential for declared service `openai`):

- **Production (forward → vault DO `#proxyRequestInner`, row.length===0
  branch at `src/vault-store.ts:472-481`):** body is
  `{"error":"not_found","service":"openai"}` (Shape V).
- **Dev/in-memory (`vault-proxy.ts:146`: `req.storedCredential === null
  → rejection(404)` at `:448-452`):** body is `CONSTANT_TIME_ERROR_BODY` =
  `{"error":"unauthorized","reason":"credential not available or caller not authorized"}`
  (Shape R).

**Probe.** Authenticated attacker POSTs `/vault/proxy/openai/v1/x`,
reads `error` field of the 404. `"not_found"` → production VaultDo
binding active. `"unauthorized"` → dev InMemory fallback (env.VAULT_STORE
missing). 1 probe → deployment substrate fingerprint.

**Amplification.** 1 RPC : 1 bit (substrate identity). Compounds with
silent-fallback risk: if `env.VAULT_STORE` binding is accidentally
dropped from `wrangler.toml`, `selectCredentialStore` at line 131
silently routes through `InMemoryCredentialStore`. Every authenticated
404 then advertises "no production vault wired" to the wire.

**Spec violation.** `error-responses.md§"Two distinct shapes"` claims
R + V collapse the "you don't have access" outcome to two byte-equal
shapes "one per layer of the proxy." In reality R is emitted by the
InMemory store branch and V by the DO branch — the shapes encode
*which store served the request*, not *which layer rejected it*.

**Closing playbook.**
1. Give `InMemoryCredentialStore` a `forward` method that emits Shape V
   on map-miss (byte-equal `{"error":"not_found","service":svc}`); OR
2. Change `vault-proxy.ts:146` (`if (req.storedCredential === null)
   return rejection(404)`) to emit Shape V instead of `CONSTANT_TIME_ERROR_BODY`.
   Then Shape R is reserved for route-layer rejection (lease,
   undeclared-service) and Shape V for credential-layer rejection —
   matching the documented semantic.

**Pinning test.** Cross-store golden:

```ts
const dev  = await routeWith(new InMemoryCredentialStore()).handle(req, envNoVault);
const prod = await routeWith(undefined).handle(req, envWithVault);
assert.strictEqual(await dev.text(), await prod.text());
assert.strictEqual(dev.status, prod.status);
```

**Confidence.** High.

### O4 — R-vs-V split enumerates manifest service registry **[P2]**

### O6 — Vault DO timing equalizer is input-length-asymmetric **[P3]**

**Evidence.** `src/vault-store.ts:472-481` (no-row branch) runs
`void checkAccess([], callerSub)` as the timing equalizer.
`vault/src/vault.ts:202-207`:

```ts
export function checkAccess(allowedSubs: string[], sub: string): boolean {
  if (/[\x00-\x1f]/.test(sub)) return false;
  return allowedSubs.some((pattern) => globMatch(pattern, sub));
}
```

`Array.prototype.some` over an **empty array** returns `false` in
near-zero time. The row-present branch at `:487` runs
`checkAccess(allowedSubs, callerSub)` with up to 64 patterns each up
to 512 bytes (`CREDENTIAL_LIMITS`). `globMatch` does `.split('*')` +
`startsWith` + `endsWith` + repeated `indexOf` — O(allowedSubs.length
× avg pattern length).

Compounding: row-present branch also does `JSON.parse(allowed_subs_json)`
at `:485` which the row-absent branch skips. Another input-size
asymmetry the equalizer doesn't cover.

**Probe.** Aggregate timing: 10⁴ requests for `(known peerFp,
candidate service)`. Compare to baseline for `(known peerFp,
known-absent service)`. Distribution shift indicates row existence
for `candidate`.

**Bit leaked.** Row existence at `(subjectFp, service)` for the
caller's *own* subject_fp. Aggregate → enumerates the caller's
credentials table. NOT cross-subject (the SQL `WHERE subject_fp = ?`
filter is load-bearing).

**Closing playbook.**
1. Also run `JSON.parse(stub_json)` + same-length `checkAccess` with
   a precomputed stub (64 × 512-byte no-match patterns) in the
   no-row branch.
2. Better: SELECT 1 existence probe first, branch into a
   constant-cost dummy decrypt + glob whether or not the row exists;
   actual decrypt only fires when both row existed AND access passed.

**Pinning test.** Per threat-model §9.4.b playbook,
`assertTimingWithinQuantization(noRowMedian, denyMedian, 1)` —
|delta| < workerd's 1ms `performance.now()` floor across 10³
trials. Skipped today.

**Confidence.** Medium (cost is real; may not cross workerd
quantization today, but `allowedSubs` length is operator-controlled
and could grow).

### O7 — Receipt-emission absent on forward path — load-bearing claim #3 broken **[P2]**

**Evidence.** `wire/receipt-commitment.md` requires receipts on
success OR upstream error (Shape U), NOT on 404/401/429.

The legacy `resolve`-path runs `proxyWithReceipt` at
`vault-proxy.ts:209-258` which emits one receipt per call.

The production `forward`-path at `vault-proxy-route.ts:176-183` just
returns `credentialStore.forward(...)` verbatim — **no receipt-emit
wrapper**. Vault DO's `#proxyRequestInner` at `vault-store.ts:498-505`
returns the upstream response directly. End result: **production
emits zero receipts for any call.**

**Bit leaked.** This is the inverse: a *receipt-absence* signal.
Observer with access to `peer_receipts` writes can distinguish "route
ran in legacy in-memory mode" (receipts present) from "route ran in
DO-forward mode" (receipts absent). More importantly, the
`README.md§"Load-bearing claims"` claim #3 (*"Audit by receipt —
every proxy call commits to peer_receipts row"*) **does not hold in
the production composition**. A briefly-compromised in-cluster bundle
holding a valid lease can verify "my calls leave no audit trail" by
counting receipt rows.

**Closing playbook.**
1. Wrap the `credentialStore.forward(...)` call at
   `vault-proxy-route.ts:177` with a receipt-emit shim (capture
   peerFp, service, response.status, sizes, ts, nonce on return).
2. OR have vault DO itself emit receipts via the ADR-0003
   content-addressed handoff to TrustStore.

**Pinning test.** Integration test running the route in DO-forward
mode + asserting `peer_receipts.size > 0` after a happy-path call.
None exists today.

**Cross-ref:** Overlaps with observability-friend's
silence-is-evidence scope.

**Confidence.** High.

### O-OBS-1. Forward path emits ZERO receipts — §13.2 silence-is-evidence dead on production traffic [P1]

**Evidence.** `src/routes/vault-proxy-route.ts:176-183` — when
`credentialStore.forward` is defined (always true for
`VaultDoCredentialStore`), the route returns the Response from
`credentialStore.forward(...)` directly. This branch **never reaches
`vaultProxyHandler`**, which is the only thing that emits
`ProxyCallReceipt` (`src/routes/vault-proxy.ts:225-242`, inside the
`finally{}` of `proxyWithReceipt`).

`src/vault-store.ts:391-506` (`CredentialVault.proxyRequest`) also
emits no receipt. `grep -rn ProxyCallReceipt --include="*.ts"` finds
**two files**: `src/routes/vault-proxy.ts` and
`test/routes/vault-proxy.test.ts`. Neither vault DO nor the forward
adapter ever constructs one.

Compounding: `src/manifest/runtime.ts:186-189` instantiates
`VaultProxyRoute` with `{services}` only — no `receipts`, no
`metrics`. Even on the in-memory fallback path the emitters are
`undefined` at request time, so the conditional emits at
`vault-proxy.ts:225` and `:243` are dead in production. **Zero
receipts emit for any production cred-iso/v1 call**, vault-DO or
in-memory.

**Gap shape.** `wire/receipt-commitment.md:80-96` (§"Emission
ordering") declares: "Receipts are emitted exactly once per
`POST /vault/proxy/...` request, regardless of outcome ...
Conformant implementations MUST NOT batch or defer emission beyond
the request's lifetime — silence-is-evidence (ADR-0007 §13.2) breaks
otherwise." The deployed code emits zero. A disclosure-endpoint
query `GET /interlace/peers/<fp>` returns no cred-iso/v1 receipt
rows for **any** peer, ever. Auditors cannot distinguish "peer X
never exercised any service" from "peer X exfiltrated every
credential A through Z via the proxy" — both look identical (empty
receipt set).

**Attack relevance.** This isn't an edge case — it's the **default
production path**. Every authenticated proxy call, including those
that successfully return upstream-secret-derived 2xx responses,
generates zero audit trail. An attacker holding a valid lease
against a peer fingerprint can hit `/vault/proxy/openai/v1/chat/completions`
N times and the post-incident forensics question "what did peer X
proxy?" has no answer. Master statement §"What load-bearing means
here" claim #3 ("Audit by receipt — every proxy call commits to
peer_receipts row") is currently false.

**Defense.**
(a) `VaultProxyRoute.handle` must wrap the forward branch in a
measure-and-emit shim — same shape as `proxyWithReceipt` (start
clock, capture sizes, build canonical receipt, emit in `finally`).
The vault-DO response is already a `Response` so size + status are
available without touching plaintext.
(b) `src/manifest/runtime.ts:187` must pass a real `receipts`
emitter (writing to TrustStore.peer_receipts via the cross-DO
handoff pattern in ADR-0003/0012). The current `{services}`-only
deps instantiation is the proximate cause.
(c) Add a Phase-7 conformance test asserting receipt-row count == 1
after a forward-path call — would have caught this immediately.

**Confidence.** High. Verified by grep across `src/` + manual walk
of both code paths.

**Cross-ref.** Enumeration-oracle-hunter O7 also notes
receipt-emission absence on forward path (different framing —
disclosure-side audit-claim breakage). Same root cause; merge in
synthesis.

### O-OBS-3. No startup OR per-request signal of which CredentialStore branch ran — silent dev-mode-in-prod [P1]

**Evidence.** `src/routes/vault-proxy-route.ts:125-132`
(`selectCredentialStore`) silently falls through to
`InMemoryCredentialStore` when `env.VAULT_STORE` is missing. No
`console.log` anywhere in the selection path. No metric. No
startup-time check in `src/index.ts` or `src/manifest/runtime.ts`
that asserts `env.VAULT_STORE` is present when
`INTERLACE_ROOT_PUBKEY` is also set (i.e. "auth-on means prod, and
prod means vault must be wired"). The `InMemoryCredentialStore`
constructor opens with `_opts: {dev: true}`
(`src/routes/vault-proxy-credential-store.ts:92-97`) explicitly to
be grep-able — but nothing grep-checks it at deploy time.

**Gap shape.** Operator deploys cloister with
`INTERLACE_ROOT_PUBKEY` set (auth on, looks production), but forgets
to add the `VAULT_STORE` DO binding in `wrangler.toml` /
`config.capnp`. Result: every request gets a constant-shape 404 from
`vaultProxyHandler`'s `req.storedCredential === null` check
(`src/routes/vault-proxy.ts:146`) because InMemoryCredentialStore is
empty. From the wire this looks identical to "no credentials
declared for this peer/service yet." Operator may think "we just
haven't put any creds in yet" and never realize the entire vault
substrate is absent. Worse: a phantom-vault deploy where some
provisioning path succeeds against in-memory storage, gets lost on
the next Worker eviction, and produces intermittent
"credential not found" errors with no signal that the storage layer
is volatile.

**Distinguishability question.** From the operator's POV, "missing
binding" is indistinguishable from "binding present, no rows yet."
From the auditor's POV (per O-OBS-1), zero receipts in either case.

**Attack relevance.** No active attacker required for the
misconfiguration — but an attacker who notices the deploy is using
in-memory mode (e.g. by observing eviction-correlated cred-loss) can
game the provision-then-evict cycle. Higher value: an operator can
ship a "production" deploy that is actually running dev-mode and
have no signal until forensics.

**Defense.**
(a) Startup-time fatal check in `src/index.ts` or `runtime.ts`: if
`env.INTERLACE_ROOT_PUBKEY` is set and `env.VAULT_STORE` is absent,
log a loud `console.error` AND refuse to handle `/vault/proxy/*`
requests (return 503 with an operator-readable body, not the
constant-shape 404 — this case is operator-facing, not attacker-facing,
so wire-distinguishable is OK).
(b) One-shot `console.info({event: "vault.cred_store_selected",
branch: "vault-do" | "in-memory" | "explicit", bundleIdName:
"router"})` at first `selectCredentialStore` call. Memoize so it
logs once per Worker instance.
(c) Health endpoint expansion: `/health` (if it exists today —
verify; no `/health` route was found in `src/routes/` during this
audit) should touch
`env.VAULT_STORE.idFromName("router").fetch(...)` (returning the
405 stub from `vault-store.ts:508`) so a missing binding fails the
health probe — currently the health signal is decoupled from vault
reachability.

**Confidence.** High.

### O-OBS-4. 502 `upstream_unavailable` is wire-visible but internally silent — vault-DO outages don't alert [P1]

**Evidence.** `src/routes/vault-do-credential-store.ts:86-92`:

```ts
try {
  const stub = ns.get(ns.idFromName(this.bundleIdName)) as ...;
  return await stub.proxyRequest(peerFp, service, callerSub, request);
} catch {
  return jsonResponse(502, { error: "upstream_unavailable" });
}
```

Bare `catch` with no variable bound, no `console.warn`, no metric,
no receipt. The error vanishes — only the caller sees the 502. The
catch swallows EVERY throwable: workerd RPC timeout, DO eviction,
KEK source failure (the `#getKEK()` reject path at
`vault-store.ts:524` is documented as recoverable per
cloister-2176e4 — but a recoverable internal error becomes an
invisible 502 here), validation throws, anything from the `vault/`
library.

**Gap shape.** Operator pages on "cred-iso/v1 503 rate" — but the
metric doesn't exist (O-OBS-2), the failure class is 502 not 503
anyway, and the body is fully redacted. Logs are empty (no emit).
Receipts are empty (O-OBS-1). The vault DO can be melting under a
KEK-source outage or a wrangler-deploy bug and the operator's first
signal is end-user complaints.

**Distinguishability question.**
- Vault DO unhealthy + attacker sending requests → wire shows 502s,
  operator sees nothing internally.
- Vault DO healthy + upstream provider down → wire shows 502 (the
  `sanitizeResponse` of upstream's 5xx, post-decrypt) — same wire
  shape, very different operator action.
- Vault DO unreachable due to binding misconfiguration (`ns`
  undefined → caught at `vault-do-credential-store.ts:82-84` as 503
  `vault_unavailable`) → different status code, but still no log.
The three failure classes need to be distinguishable for paging /
runbook routing; today they collapse into "the deploy looks fine
because nothing's logging."

**Attack relevance.** An attacker who can induce vault DO failure
(KEK-source DoS — likely cross-cut with dos-resilience-auditor F1
findings) forces the entire cred-iso/v1 surface into 502 mode
silently while operator dashboards stay green. Combined with
O-OBS-1, the attacker also erases evidence that anyone tried.

**Defense.**
(a) Bind the caught error: `catch (e)`. Emit
`console.error(JSON.stringify({event: "vault.proxy_forward_throw",
peerFp, service, error: e instanceof Error ? e.message : String(e)}))`.
This goes to Logpush; correlatable per-peer / per-service.
(b) Emit a metric `vault_proxy_forward_error{class=rpc_throw |
binding_missing | other}` so dashboards can alert on rate.
(c) Distinguish: timeouts vs other exceptions vs "binding missing"
via distinct status codes (504 vs 502 vs 503) so operators can route
differently.

**Cross-ref.** Enumeration-oracle-hunter O2 (Shape `503
vault_unavailable` undocumented) + O3 (Shape U binding-vs-RPC timing
distinguishable) both touch this code path from the wire-shape side.
This finding is the internal-observability complement — same code,
different invariant.

**Confidence.** High.

### O-OBS-5. Spec claim "no receipt on 401/404/429" composes badly with O-OBS-1 to make silence ambiguous [P2]

**Evidence.** `cloister-spec/credential-isolation/v1/wire/receipt-commitment.md:86-91`
codifies: constant-shape 404, lease 401, rate-limit 429 → no
receipt. Rationale is sound for 401/404 (no verified peer to
attribute to; no upstream call made).

But per O-OBS-1, the SUCCESS path also emits no receipt. So the
disclosure-endpoint answer to "what did peer X do?" is empty for
**every** outcome category — success, upstream error, lease fail,
rate limit, unauthorized. The spec assumes a baseline of
success-path receipts against which the absence-of-rejection-receipts
is meaningful; if success-path is also silent, the operator's
question "did peer X attempt anything?" becomes literally
unanswerable from the receipt substrate.

**Gap shape.** A pure-spec read says "no receipt → request never
reached upstream." A code read says "no receipt → request happened,
we just didn't emit." These are opposite. Anyone reading the spec
to interpret an empty receipt set will draw the wrong conclusion.

**Defense.** Fix O-OBS-1 first; rejection-path silence becomes
meaningful again. If fixing O-OBS-1 is deferred past first
production traffic, the spec MUST be amended to say "v1
implementations are exempt from emission requirements pending
cloister-XXXXXX" so no operator interprets the silence as evidence.

**Confidence.** High that this composes with O-OBS-1; Medium that
it warrants a separate finding (could fold into O-OBS-1 synthesis).

### O-OBS-6. Lease-counter advances on forward path, but receipt-chain "second half" is uninstantiated [P2]

**Evidence.** `defaultLeaseVerifier`
(`src/routes/vault-proxy-route.ts:210-230`) calls
`verifyAndUpsertLease`, which advances `peer_lease_counters` inside
TrustStore via `verifyLeaseAndAdvanceChain`
(`src/routes/lease-middleware.ts:518`). Good — happens BEFORE the
forward branch, so the request-side counter advances even for
forward-path calls. The §13.2 "two halves of the receipt" invariant
requires the response-side to advance the attestation chain.

Per `receipt-commitment.md:69-72`: "each new receipt's hash is
computed over (canonical-receipt-bytes ‖ prev-receipt-hash)." That
chaining requires the receipt to actually be emitted (O-OBS-1) AND
persisted into a chain-aware store. Today:
- request-side counter: advances (correct)
- response-side receipt: not emitted (O-OBS-1)
- chain hashing: never happens (no receipts to chain)

So `peer_lease_counters` advances for every cred-iso/v1 call, but
the chain it commits to is empty. An auditor cross-checking
`peer_lease_counters.seq` against the disclosure-endpoint receipt
count will find seq ≫ receipt-count for every peer that uses
cred-iso/v1.

**Gap shape.** Today this is "expected" because receipts are
universally unemitted; once O-OBS-1 is fixed, **historical data
will have an unbridgeable gap** — pre-fix calls advanced the counter
without emitting receipts, and you cannot retroactively reconstruct
the chain.

**Defense.** When fixing O-OBS-1, include a one-shot migration:
rotate the chain's genesis hash and document the rotation point so
post-fix chain validation skips pre-fix counter rows. Operators
querying historic peer activity will need both pre-fix and post-fix
queries.

**Confidence.** Medium — depends on whether O-OBS-1 fix lands
before any production cred-iso/v1 deploy. If pre-production, the
migration concern collapses; the finding becomes "ensure O-OBS-1
fix lands before first prod traffic to avoid chain orphans."

### Cross-cut findings

#### Cross-cut X-1 — "The forward path is observably a black hole" (P1)

**Source beads:** Oracle O7 + Obs O-OBS-1 + Obs O-OBS-2 + Obs O-OBS-3
+ Obs O-OBS-4 + DoS F1 + Bundle F6 (auditor catch).

**Root cause.** D-track shipped `VaultDoCredentialStore.forward` as the
production substrate for cred-iso/v1, but the route layer
(`vault-proxy-route.ts:176-183`) returns the forward Response verbatim
with **no instrumentation shim**. Six emit obligations land on that
return statement and none of them fire:

1. `peer_receipts` row (per `wire/receipt-commitment.md§"Emission
   ordering"` — MUST emit per call, success or upstream-error) — Oracle
   O7, Obs O-OBS-1.
2. `vault_proxy_call{...}` metric (`vault-proxy.ts:247-255` is the only
   site; bypassed) — Obs O-OBS-2.
3. Structured log on `forward_throw` catch (`vault-do-credential-store.ts:86-92`
   bare `catch{}`) — Obs O-OBS-4, DoS F1.
4. One-shot startup log of selected branch (`vault-do` vs `in-memory` vs
   `explicit`) — Obs O-OBS-3.
5. Receipt-chain "second half" advancing in lockstep with
   `peer_lease_counters` — Obs O-OBS-6.
6. Per-peer denial counter for 5xx-rate-based quarantine — DoS F1.

**Why this is one finding, not six.** All six are direct consequences of
the same architectural choice: the route layer trusts the
`CredentialStore.forward` Response as the unit of work and emits nothing
around it. `manifest/runtime.ts:187` compounds this by instantiating
`VaultProxyRoute` with `{services}` only — `receipts` and `metrics`
emitters are `undefined` at compose time, so even if the route called
them, they'd no-op.

**Master-claim impact.** Claim #3 (*"Audit by receipt — every proxy call
commits to peer_receipts row"*) is **currently false** in production.
An attacker holding a valid lease can hit any service N times; post-
incident forensics has no audit trail to consult. The disclosure
endpoint returns empty receipt sets for every peer for every outcome
(Obs O-OBS-5 makes this point precisely — silence is no longer
evidence, it's the *default*).

**Prescription.** Single architectural fix: wrap the forward branch in a
`forwardWithReceipt` shim that mirrors `proxyWithReceipt`'s
start-clock + capture-sizes + emit-in-finally shape, AND pass real
`receipts` + `metrics` emitters from `runtime.ts`. Three files, ~80
LOC. Ships as one bead, closes six findings. **Highest-priority work
of this cycle.**

#### Cross-cut X-2 — "Error shapes silently encode substrate" (P1)

**Source beads:** Oracle O1 + Oracle O2 + Oracle O4 + Bundle F2 +
Bundle F5 + DoS F4 + Obs O-OBS-4.

**Root cause.** The same constant-time-404 contract that protects
§9.4.b is fractured across *seven* error-emission sites that each
implement it independently — three different body shapes, four
different status codes, zero shared header policy. The fracture
encodes three secrets onto the wire:

1. **Substrate identity** (O1): `error: "not_found"` (VaultDo) vs
   `error: "unauthorized"` (InMemory) discriminates production from
   dev composition in one probe.
2. **Service-registry membership** (O4): `error: "not_found"` (declared,
   no row) vs `error: "unauthorized"` (undeclared) discriminates
   manifested services from undeclared ones — full registry
   enumeration in O(dictionary).
3. **Vault-binding state** (O2): `error: "vault_unavailable"` 503 is a
   fourth undocumented shape that fires when `env.VAULT_STORE` is
   missing inside a `VaultDoCredentialStore` constructor — leaks
   composition-root state to the wire.

The composition footgun (Bundle F2 — falsy-`forward` silently
downgrades to plaintext-in-route) is the same shape one level up: the
interface allows `forward?` to be optional, so a future store that
fails to implement it produces a Shape-R 404 (InMemory's
constant-shape body), which by O1's analysis advertises "dev mode" to
the wire while ALSO breaching ADR-0013's slice-grant invariant
(plaintext bytes in route memory). Two distinct bugs, one
manifestation.

Cache-Control: no-store absence (Bundle F5 / Oracle O5 / DoS F4)
amplifies all three: an intermediary cache can pin any of these
oracle responses and amortize the leak across millions of probes for
zero attacker cost. The spec at `wire/error-responses.md:124-128`
requires `Cache-Control: no-store` on every error; the code emits
it on **none** of the six audited sites.

**Master-claim impact.** Claim #4 (*"§9.4.b constant-time 404 — peer-
existence + credential-existence non-distinguishable from the wire"*)
is **eroded today** — wire body discriminates 3 axes (substrate,
registry, binding-state) the constant-time-404 contract said it
wouldn't.

**Prescription.** Three-part fix in increasing scope:
1. **Header policy:** single `ERROR_HEADERS` const used by all seven
   sites. ~10 LOC + lint. Closes O5, F4, F5.
2. **Body collapse:** make `InMemoryCredentialStore` emit Shape V
   on map-miss (or change `vault-proxy.ts:146` to emit Shape V); make
   undeclared-service 404 emit Shape V; collapse 503 vault_unavailable
   into Shape U 502. ~40 LOC. Closes O1, O2, O4.
3. **Interface tightening:** make `forward` REQUIRED on
   `CredentialStore`; ship `InMemoryCredentialStore.forward` as an
   explicit-opt-in stub that emits Shape V. ~20 LOC. Closes F2 and
   prevents the regression class.

Each part is independently shippable; together they restore claim #4.

#### Cross-cut X-3 — "bundleIdName: 'router' literal defeats ADR-0021's seam" (P2, escalates to P1 when notme-as-bundle ships)

**Source beads:** Bundle F4 + DoS F2 + DoS F6 + Obs O-OBS-7 + Oracle O8.

**Root cause.** `vault-proxy-route.ts:128` hardcodes
`bundleIdName: "router"`. ADR-0021 designated this string as **the**
per-bundle isolation seam ("binding layer = which DO instance,
keyed by name"). Today the seam is a literal; tomorrow it's a
single-line copy-paste away from collapsing all bundles into one
shared DO. Five distinct symptoms:

- **Isolation** (F4): two `vaultProxy` routes inherit the same name
  via auto-select → share `idFromName("router")` storage.
- **DoS** (F2): the 16-slot `MAX_INFLIGHT` cap is per-DO-instance, so
  *every* peer in the cluster contends for the same bucket. One
  attacker peer with a valid lease + 16 slow-upstream connections
  denies the entire cluster.
- **DoS** (F6): the documented `vault-store.ts:14-15` convention is
  `idFromName("cluster")` for vault-DO singletons. The route uses
  `"router"`. Either the doc is stale or this route is wired to the
  wrong DO instance. Either way the inconsistency is itself a
  finding.
- **Observability** (O-OBS-7): no log emits the chosen name; a
  collision is silent.
- **Oracle** (O8): audit confirms no caller-controllable path
  influences the literal today, but the hardcoding makes future
  attacker-influence shapes possible (per-bundle env propagation
  not yet designed).

**Master-claim impact.** Claim #5 (*"Per-bundle isolation via
`idFromName`"*) holds **today only because today there is exactly one
manifest-instantiated vaultProxy route**. The instant a second one
ships, claim #5 silently becomes false.

**Prescription.** Lift `bundleIdName` out of the route literal. Three
options ranked by safety:
1. **Manifest field** (best): add `bundleIdName: string` to the
   `vaultProxyRoute` capnp schema; plumb through `instantiate()`;
   default-but-warn at compose time if unset. Schema bump (per ADR-0004
   append-only rule).
2. **Constructor dep**: require `bundleIdName` in `VaultProxyRouteDeps`;
   manifest builder supplies it. No schema bump but the manifest layer
   still has to compute it.
3. **Env binding**: read `env.CLOISTER_BUNDLE_NAME`; cheapest but
   couples bundle identity to env-var hygiene.

In all three, add a build-time lint that asserts no two `vaultProxy`
routes resolve to the same `bundleIdName`. Today's single-bundle
deploy is safe; the prescription is to *make ADR-0021's seam an
enforced contract before the second bundle ships*.

#### Cross-cut X-4 — "Manifest declares what the forward path ignores" (P2)

**Source beads:** Bundle F1 (alone, but composes with X-1 + X-2).

**Root cause.** `defaultAllowedSubs` on the `vaultProxyService`
manifest field appears to be the operator's access-control declaration
("only `skill/openai/*` may use this credential"). On the resolve+inject
path, `vault-proxy.ts:139-141` enforces it. On the forward path —
the production path — it is dead code: `vault-proxy-route.ts:176-183`
delegates without consulting it. Row-level `allowed_subs_json` inside
vault DO is the only enforced ACL, set by `putCredential` (which is
out-of-band from manifest review).

This produces a **two-ACL system where which ACL fires depends on a
composition-root decision invisible at manifest review**. The
operator-facing footgun: tighten the manifest to `["skill/openai/*"]`,
see green tests on the in-memory resolve path, ship to production
which runs forward path, manifest gate silently dropped, row-level
glob (possibly `"*"` from an earlier put) wins.

**Master-claim impact.** Claim #2 (*"Identity-scoped access —
`allowedSubs` glob enforced before injection"*) is true at the row
level but **not at the manifest level on the forward path**. The
operator-facing interpretation of "scoped" doesn't match the
implementation.

**Prescription.** Either (a) run `checkAccess(serviceConfig.defaultAllowedSubs,
verifiedLease.peerFp)` BEFORE `store.forward(...)` on the forward
branch (layered: manifest gate at route, row gate inside DO); or (b)
amend `cloister-spec/credential-isolation/v1/README.md` to document
that `defaultAllowedSubs` is **only** a `putCredential`-time default,
not a request-time gate. (a) is preferable — the docstring at
`vault-proxy-route.ts:165` already advertises layered enforcement,
and adversarial review (Bundle F1) shows operators will read it
that way.

#### Cross-cut X-5 — "Lease verification is a cross-route amplifier with no fast-path" (P2)

**Source beads:** DoS F5 (alone, but composes cluster-wide).

**Root cause.** Per the route's contract, `verifyAndUpsertLease` runs
**first** in `handle()` — cert-chain wasm verify + Ed25519 sig verify
+ TrustStore RPC + epoch + validity-window + nonce-dedup, per request,
per peer, with no cache. An attacker holding any valid lease can
probe-spam the route at 1 HTTP POST cost-to-attacker per request, and
6+ expensive operations + 1 cross-DO TrustStore write cost-to-defender.
Per cycle-1 (2026-05-12), the TrustStore is a *cluster-wide singleton
DO*; saturating it slows lease verification for **every** route in
**every** isolate in the cluster (McpEdge, disclosure, future routes).

Today the upper bound is set by notme's cert-mint rate (which we
trust). Tomorrow: any attacker with a single long-lived lease is the
upper bound.

**Master-claim impact.** Doesn't break a numbered claim, but the
implicit "lease verification is cheap" assumption baked into the
threat model § §8 design needs revisiting.

**Prescription.** Per-peer "successful lease verification" cache with
short TTL (5-15s) keyed by lease-header-bytes hash, invalidated by
epoch advance or explicit TrustStore signal. Per-peer denial counter
at the route layer for fast-reject before lease verify. Out of scope
for this cycle's fixes; file as a P2 substrate-wide bead and queue
for next cycle's design pass.
