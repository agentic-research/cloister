## Cross-cut findings (NEW this cycle)

### Cross-cut A — "Implementation drift from documented threat model"

trust-root-friend's seven findings on PR #1 share a structural shape:
the implementation does not enforce what the spec promises. The
helper's own source comments (in `ratelimit.rs:13-23` particularly)
**assert defenses that don't exist** — claiming OS process scoping
prevents cross-UID access when no such mechanism applies. This is more
dangerous than a missing defense: it's a defense that reads as
implemented to a reviewer skimming the code.

**Cross-cut prescription.** Each ADR with normative requirements (the
MUST/MUST-NOT bullets) needs a corresponding test that asserts the
requirement is enforced. dos-friend's pilot landed test pinning for
F1+F3+F4 directly. trust-root-friend's findings landing as a §15
threat-model section + tests (`tests/host_adversarial.rs`) on PR #1's
branch follows the same pattern. **Going forward: every ADR with
normative requirements should ship with a matching test file.** This
becomes a checklist item for code-architect when ratifying new ADRs.

Source beads: 15.1–15.7 (`cloister-7aaab1`, `-7afedc`, `-7b5b9d`,
`-7bb456`, `-7c2179`, `-7c737a`, `-7cd202`).

### Cross-cut B — "Identity propagation is the missing axis"

dos-friend's F2 (`cloister-2140b5`, resolved by ADR-0021) and
trust-root-friend's 15.2 + 15.3 (cross-UID loopback + wrong rate-limit
identity) share the same root cause: **the substrate has no
mechanism for asserting "who is calling me" at substrate-layer
boundaries.** Vault's identity-propagation question (now ADR-0021)
and the helper's per-caller authentication question are two
manifestations of the same gap.

**Cross-cut prescription.** Identity-at-syscall is a substrate-wide
concern that should be addressed once, not per-component. Worth a
follow-on ADR — call it ADR-0022 — that picks the identity
propagation mechanism (per-bundle DO + UDS+peer-cred? bearer token +
manifest-pinned shared-secret rotation? something else?) and applies
it uniformly to vault, helper, and any future syscall-shaped surface.
**Filing as `cloister-future-identity-syscall` (placeholder bead;
upgrade after next cycle's isolation-friend pass adds more datapoints).**

## What worked

- **Pre-merge dispatch on a real PR.** trust-root-friend's pass on
  PR #1 caught a master-key-exfil regression *before* the PR
  merged. This is exactly the value-capture the rotation was
  designed for. Filing as the load-bearing precedent: dispatch
  trust-root-friend / isolation-friend pre-merge on any PR that
  touches the trust-root surface or the manifest schema.

- **Read-only specialist + write-access synthesis-lead boundary.**
  Specialists filed beads; synthesis-lead promoted to threat-model
  rows + cycle report. No specialist tried to "fix" their own
  finding, which kept the engineering-team-decides-the-fix boundary
  clean.

## What didn't work

- **Five of seven specialists not yet dispatched.** Pioneer-mode
  drift visible in our own rotation: we're under-resourcing
  specialists whose findings are speculative-looking (silence-friend,
  oracle-friend) and over-indexing on ones with concrete recent
  trigger (dos, trust-root). Next cycle: dispatch at least three
  more specialists even if the threat surface looks "thin" — that's
  exactly where unknown unknowns hide.

- **Tests-against-the-threat-model didn't land alongside the §13.6
  row earlier this session.** The pattern only emerged from cross-cut
  A in this cycle. Going forward, no threat-model row lands without
  a pointer to a test (even if the test is "documented gap; not
  testable at this layer").
