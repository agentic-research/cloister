# ADR-0073: Resource facts are imported, never granted

Tracking bead: `cloister-85999c`. Research:
[IaC graphs as cloister graph input](../research/iac-graphs-as-cloister-input-2026-11-11.md).

## Context

Operators already describe their infrastructure in Terraform or OpenTofu.
Those tools render what they manage as a documented JSON document
(`terraform show -json`), with resource types, resolved attributes and a
marker for each sensitive value. Cloister's graph has a forwarded side
(ADR-0070 §2) that is typed by hand today: which Worker binds which service,
what a tunnel routes to, where a database lives.

Reading the rendered document fills that side in without restating it. It
also carries a risk that this ADR exists to close: an operator's
infrastructure is often more permissive than their intent. If finding a
binding in Terraform state could make it an authorized edge, importing a loose
configuration would quietly grant access nobody declared.

## Decision

### 1. An importer produces facts, and a fact cannot carry authority

`importFacts(document)` returns resource facts. A fact has exactly five
fields: `source`, `address`, `type`, `name`, `attrs`. There is no grant,
connection, edge or wire field, and the constructor refuses one by name. So
"discovered is not authorized" is a property of the type. It doesn't depend on
reviewer discipline.

Only a declaration in `cluster.toml` grants anything. A report can show a
fact beside a declaration. Nothing turns one into the other.

### 2. Input is a rendered document, and cloister runs no tool

The importer reads the output of `terraform show -json` or `tofu show -json`,
state or plan, that the operator rendered. It doesn't run Terraform, read a
backend or parse HCL (ADR-0070 §2: rendered output only, with a real parser).
It refuses a `format_version` major it doesn't know. It also refuses the raw
`.tfstate` file, which is not a documented format.

### 3. The attribute set is a data mapping, validated against the provider's published schema

What is read is data: `cli/lib/facts/mappings/cloudflare.json` names, per
resource type, the attribute paths to copy, the ids kept as join keys, the
nested lists, and the relations. A projection of the provider's own schema
(`tofu providers schema -json`), generated by `scripts/gen-facts-spec.mjs` and
vendored, validates that mapping when the module loads. It refuses by name:
- a type or attribute the provider doesn't have;
- an attribute the provider marks sensitive;
- a read, name or id path that isn't a scalar;
- a relation whose target type or attribute doesn't exist.

An attribute the mapping doesn't name is never read. The importer doesn't read:
- a Worker's source;
- the value of a binding (`text`, `json`, key material);
- a tunnel secret;
- who an Access policy admits;
- a DNS record's content, or a private service's host.

A mapped attribute that the document marks in `sensitive_values` is dropped
too. If a whole list is marked sensitive, the list is withheld and the report
says so.

Relations are exact joins: a value equals a mapped attribute of another
resource, or it matches nothing and is reported as "not in this document".
Nothing is matched by guessing at a name.

A provider often lets one attribute name its target in more than one
spelling. The Google provider accepts a short name or a full resource path for
an IAM binding's target and writes the full path back to state, while the
target keeps its short `name`. Comparing the binding against `name` alone never
matches in state.

The answer is not to parse the identifier. Every provider already exposes a
resource's full identifier as an attribute of that resource (`id`, `arn`), so
the mapping lists the target attributes to compare against and each comparison
stays plain equality. Three options, all data and none tied to a provider:

- `toAttr` may be a list of alternatives, tried in order, most exact first.
- `scope` lists attributes (a project, a region, an account) that must be
  equal wherever both resources state them. A candidate is dropped only by a
  stated difference.
- `stripPrefix` removes one declared leading string from the value first.

The first alternative with exactly one candidate wins. Several candidates for
the same alternative leave the relation unresolved, so two resources with the
same short name are never confused. An identifier that equals no target
attribute is not taken apart and matched by its last segment.

How a mapped type appears in the report is data too. A type with a `report`
block is listed under the section it names, with the attributes it says to
show. A type with an `access` block is a row that says who may do what: it
names its role and principal attributes, the roles to show and their labels,
and the principals that mean "anyone", and it belongs to the resource its
relation resolves to. Both blocks may name only attributes the entry already
lists under `read`. So adding a resource type, or another cloud, is a mapping
entry and a regenerated spec, with no report code. Access rows are not
authoritative: a resource with no row for a label is reported as "unknown",
never as "none". The Cloudflare sections predate this and are still written by
hand in the report.

**Nested blocks, and the edges nobody declared (2026-11-18).** A resource's
structure is not only attributes. A Cloud Run service keeps its containers,
their env, args and ports in nested blocks (`template` → `containers` →
`env`). A mapping's `lists` path may now walk through such blocks, and through
a list on the way to another list. The spec projection includes a block only
when a mapped path goes through it. The values and the document's
`sensitive_values` are walked side by side, and a list whose marker is `true`,
malformed or too short is withheld and reported as withheld. Terraform marks a
whole set sensitive when one element is, so one secret env value withholds the
container's whole env.

Those strings are where the graph nobody declared is written. A reported type
may declare an `address` (the attribute holding where it is reached) and
`dials` (which of its own strings may name another resource's address). The
report then lists what each resource dials, from two exact sources, and says
which:

- **By address.** A string the resource starts with holds the host of another
  resource's address. This is the usual source in a state document, where
  addresses are concrete. A host that is the address of two resources resolves
  to neither.
- **By configuration.** In a plan, an address is often unknown until apply,
  but `configuration` records that the value is taken from another resource.
  The reference is found inside the nested block, and the row's own constant
  name says where: `env RECONCILER_URL`. This works even when the env values
  themselves are withheld.

A dialled edge is an observation, like every fact. Values are never printed:
only the target and where the string was.

A plan document adds one more source for a join. A value that is unknown until
apply (a route's `script`, a version's `worker_id`) is absent from
`planned_values`, but `configuration` records which resources the expression
references. For the attributes a mapping lists under `referenceAttrs`, a fact
keeps those root-module resource addresses (exactly `<type>.<name>`; `var.`,
`local.`, `data.`, `module.` and attribute paths are dropped). A relation uses
them only when value equality found nothing, the document is a plan, and
exactly one referenced address has the relation's target type. Zero or several
candidates leave it unresolved. A state document never uses them. Account, zone and resource ids are
kept only as join keys, so the report can resolve a binding to a name. They
are not printed.

### 4. A rendered document is a secret, and the tool treats it as one

`show -json` prints every secret in the state in plain text. So:
- `cloister inspect` refuses an input file that git tracks.
- Committed fixtures are synthetic. A test holds them to reserved example
  names and ids made of one repeated digit.
- Nothing from a run against real infrastructure is written anywhere.

### 5. The first consumer is a report with three findings

`cloister inspect --terraform <file>` lists what the document describes. With
a `cluster.toml`, it compares each declared wire against the document:

| Finding | Meaning | What it does not mean |
|---|---|---|
| `evidenced` | a declared wire has a matching binding | that the binding is the only path |
| `unknown` | a declared wire has no matching binding in this document | that the edge is unenforced; the evidence may live elsewhere |
| `undeclared` | the document binds one workload to another and no wire declares it | that the edge is now allowed; it is reported and nothing else |

The report changes neither input.

### 6. Cloudflare first

The first adapter reads the Cloudflare provider's types:
- Worker scripts and their bindings;
- routes;
- KV and D1;
- tunnels and their ingress;
- Access applications;
- DNS names.

A Worker's bindings live in its wrangler config, not in Terraform state, so
`cloister inspect --wrangler <file>` reads a `wrangler.toml` or `wrangler.json`
as a second source. It reads only the keys listed in
`mappings/wrangler.json` (service, Durable Object, KV, D1, R2 and queue
bindings, and routes), each checked at load against wrangler's own config
schema. It never reads `vars` or secrets. A wrangler config is normally
committed and holds nothing this tool reads, so the tracked-file refusal in §4
applies to the Terraform document only. A Worker described by both sources is
listed once.

Cloister's own production placement is Workers, and a Worker's service
bindings are the same capability edges cloister declares as `wires`. So the
comparison is exact, not approximate. Under ADR-0072 this supplies the
`workerd` realizer's facts.

**Amendment (2026-11-18): a mapped constant may be read from the plan's
configuration.** A plan has two sections. `planned_values` holds values, with
sensitivity marked. `configuration` holds the expressions as the source wrote
them: a literal, or a list of what the value references.

A mapping may name a nested block list and fields of its rows to read from
the configuration (`configLists`). For each field cloister reads one of two
things: the literal, when the expression is a constant, or the resources and
variables it references. It never evaluates an expression.

This is needed because a provider may mark an entire block sensitive when one
element of it is. The planned values of every row are then withheld, although
most rows are not secret. The configuration still tells them apart.

The same limits hold as for any mapped attribute. Every field must be a
scalar in the provider's published schema that the provider does not mark
sensitive. A value the configuration takes from a variable is never read,
whether or not the variable is sensitive: only its name is. The printed
report does not carry these rows; they are read only when a `cluster.toml` is
drafted ([ADR-0074](0074-the-graph-is-derived-cluster-toml-holds-intent.md)
§7). A literal secret typed into the configuration would be copied into that
draft as an env value. It is already in the operator's source, and the draft
is theirs to review before it is committed.

**Amendment (2026-11-19): three things a mapping may say, so a provider
shaped like Kubernetes needs no code.** Reading Kubernetes resources declared
in Terraform needed nothing provider-specific, but it needed the reader to
understand three shapes it had not met. Each is available to every mapping,
and each is held to the provider's schema by the validator:

- **A scalar inside a single nested block.** `metadata.name` is a path through
  a block the document renders as a list of one. A list of none, or of
  several, has no one value, so the path reads as absent.
- **An address that is built, not stored** (`report.hosts`). A Service is
  reached at a name made of its name and namespace. A template may use only
  attributes the entry reads, and must use at least one: a fixed host is not
  a resource's address.
- **A resource that stands for another** (`report.standsFor`). What answers
  at a Service's name is the workload whose pods its selector matches. The
  mapping names the selector map, the label map on the candidates, and the
  attributes both must share. Exactly one candidate must match. None, or
  several, resolves to nothing: an edge is never guessed. The maps are read
  under `maps`, whole, and only where the provider declares a map of strings
  it does not mark sensitive.

An entry may also say it is **`like`** another. A provider often has several
types read the same way (a Deployment, a StatefulSet and a DaemonSet all hold
a pod template, and most types exist under an old and a new name). Written
out, that is one block many times, and a mistake in one copy goes unread. An
entry that is `like` another gets everything it says, with its own
differences laid over. The named entry must be written out in full: a chain
is refused. Each expanded entry is still checked against its own type's
schema, and a test runs every mapped type, not only those in a fixture.

None of this lets a fact carry authority. A resolved Service is still an
observation that one workload names another.

**Amendment (2026-11-23): an object a resource holds whole.** Some resources
carry an object of another API whole, in one attribute their provider leaves
untyped (`dynamic` in its schema). Kubernetes' `kubernetes_manifest` holds any
Kubernetes object in `manifest`. A workload written that way was not read at
all. The report counted it under "Not read", and a check could pass because it
never looked at it. It is now read like the same object written as the
provider's typed resource:

- **The mapping declares the resource under `objects`**: the attribute that
  holds the object, and the fields that say what it is (`by`: `apiVersion` and
  `kind`). The validator checks the attribute against the provider's schema:
  it must exist, and the provider must leave it untyped.
- **Each kind it reads is a type of its own**, named
  `<resource type> <apiVersion> <kind>` (`kubernetes_manifest apps/v1 Deployment`).
  Its entry uses the object's own field names (`containers`, `containerPort`),
  not the provider's (`container`, `container_port`), so a typed entry's paths
  do not carry over. Where the names are the same (a Service's selector, a
  Namespace's name), the entry is `like` the typed one.
- **Its paths are checked against the API's own published schema**, as a typed
  entry's are against the provider's. For Kubernetes that is the OpenAPI v3
  document each release publishes (`api/openapi-spec/v3`), projected to the
  kinds the mapping reads by `gen/facts-spec.mjs --api`, at a pinned release
  (1.37.0). A test regenerates the projection byte for byte when it is given
  the documents. kubeconform validates manifests against schemas generated
  from the same documents.
- **A kind no entry reads is named on the "Not read" line**
  (`kubernetes_manifest networking.k8s.io/v1 Ingress`), not only counted. An
  object whose kind cannot be read (absent, not text, or marked sensitive) is
  counted as `kubernetes_manifest (kind not stated)`.
- **The configuration is one expression for the whole object.** It says what
  the object takes from. It does not say where in the object each reference
  sits, or which value took what. Nothing is guessed from it:
  - its references are not read as edges. An edge comes from a value (an env
    value or an argument holding a workload's address). A value that is
    unknown until apply gives no edge, and a declared connection that relied
    on it is reported unknown.
  - an env value is drafted as a constant only when the expression takes from
    nothing, so every value is the source's own text. Otherwise it is
    unknown, named with what the expression takes from. A secret reference
    names a Secret, and a value that is one workload's whole address is that
    address, so each is drafted as what it is.
- **An object that does not state its namespace has none here.** The cluster
  the provider talks to decides where it lands, and the document does not say.
  A Service's names cannot be built without one, so nothing resolves to it,
  rather than to a guessed `default`.
- **A sensitivity marker on a parent covers everything under it.** A document
  may mark a whole object sensitive. Walking past that marker found no marker
  below it, so the value under it read as public. The walk now stops at the
  marker, for every mapping. A manifest makes the case common, but any path
  two levels under a marked block could reach it.

**Amendment (2026-11-24): a custom resource is checked against its CRD.** A
Knative Service (`serving.knative.dev/v1 Service`) is a custom resource.
Kubernetes' own documents do not define it; its CustomResourceDefinition does,
in `openAPIV3Schema`. Cloister places Knative Services itself, so it reads
them back:

- **A CRD is a published schema.** `gen/facts-spec.mjs --api` reads one (YAML)
  as an input. Each version it serves is a kind, and the projection holds the
  kinds the mapping reads.
- **Its metadata is Kubernetes'.** A CRD may not describe `metadata`: every
  object's is the API server's ObjectMeta. That part is projected from a
  Kubernetes OpenAPI document, and the projection records which release
  (`objectMeta`). A test holds it to the release of the Kubernetes projection.
- **One projection per published source**: Kubernetes 1.37.0's kinds, and
  Knative Serving 1.24.0's Service. Every kind the mapping reads is defined by
  exactly one. The validator refuses a kind in none, and a kind in two.
- **A Knative Service is a workload placed `knative`, and its own address**
  (`<name>.<namespace>.svc.cluster.local`, and `.svc`). Its one port's name is
  its protocol (`http1` or `h2c`), so the protocol is read, not taken by
  convention. With no port declared it is served on 8080 over `http1`, which
  the draft says was assumed, as for Cloud Run.
- **Exposure may be one key of a map the entry reads**: here the
  `networking.knative.dev/visibility` label. `cluster-local` sorts as cluster.
  No value sorts as edge: with no label, the cluster's own default decides,
  and a plan does not state it, so it is unknown. A sort list may be empty, as
  long as some value is sorted.

## Out of scope

- Running any infrastructure tool, or reading a backend.
- Turning a fact into a declaration, even as a suggestion written to a file.
- Raising or lowering a computed channel strength from a fact (ADR-0070 §3).
  Evidence is reported next to strength. It doesn't change it.
